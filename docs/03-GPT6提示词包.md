# 03 · GPT-6 提示词包

**用法**：按顺序把 **P0 → P7** 逐个粘贴给 GPT-6（每个提示词都是一次独立的对话/任务）。
P0 是系统提示词，第一次就要给，之后每轮都保留。P8 是第 4 步修 Bug 时用的循环提示词。

**为什么这样切分**：
- **P3（战斗引擎）必须独立成一轮**，而且必须比前端先做。引擎是可验证的，UI 不是。
  先把引擎做到与参考裁判 0 差异，再写界面——否则你会在一个算错的引擎上调试动画。
- 每个提示词都带 **DoD（完成的定义）** 和 **自检命令**，GPT-6 交付前必须自己跑一遍并贴出输出。
- 所有提示词都强调"数据驱动、禁止硬编码"，这样你后续调平衡不用改代码。

> 贴提示词前，把整个 `backpack-brawl/` 目录（尤其 `docs/02`、`data/`、`tools/`）交给 GPT-6
> 作为可读上下文。它是"规格 + 可执行的裁判"，比任何文字描述都精确。

## P0 · 系统提示词（每次对话都带）

```
你是资深游戏前端+后端工程师，正在实现一款名为《背包大乱斗》的 Web 小游戏。
类型：单人 PvE 自走棋 + 背包整理（Tetris 式摆放）。参照 Backpack Battles。

【唯一权威规格】
- 规则、数值、数据结构、API 契约：docs/02-游戏策划书.md。规则冲突时一律以它为准。
- 数据：data/rules.json（全部可调数值）、data/items.json（40 件物品）、
  data/classes.json（4 职业）、data/enemies.json（18 关）。
- 参考实现（战斗结算裁判）：tools/engine.mjs。它是 docs/02 §6 的可执行版本。
- QA 工具：tools/diff-test.mjs（差分测试）、tools/qa-check.mjs（综合体检）。

【三条不可协商的工程约束】
1. 引擎与表现分离：战斗逻辑放在 packages/engine，纯 TypeScript、零 DOM/Canvas/React 依赖，
   必须能在 Node 里 headless 运行。前端只是**回放**引擎输出的 BattleLog，不得边渲染边计算。
2. 确定性：随机只能用种子化 PRNG（推荐 mulberry32），种子 = hash(matchSeed, round, 阵容指纹)。
   严禁 Math.random()、Date.now()、performance.now() 参与逻辑；严禁依赖 Object.keys 的遍历顺序；
   所有遍历必须按显式排序键（背包页, row, col）执行。
3. 数据驱动：所有数值必须来自 data/*.json。代码里出现硬编码的伤害/价格/冷却数值即为缺陷。

【代码质量要求】
- TypeScript strict 模式；所有外部输入用 zod 校验；禁止 any（必要时用 unknown + 收窄）。
- 每个模块必须有单元测试；引擎的测试要覆盖 docs/02 §6 的每一条规则。
- 函数保持纯函数优先；副作用集中在 apps/ 层。
- 命名用英文，面向玩家的文案走 i18n/zh-CN.json，不得硬编码在组件里。

【交付格式】
每轮结束时，按以下结构回复，不要省略：
1. 变更文件清单（路径 + 一句话说明）
2. 关键设计决策（尤其是与规格不同或规格未覆盖的地方，必须显式提出，不要默默决定）
3. 自检命令与**真实输出**（不许写"应该通过"）
4. 未完成项与已知问题
5. 下一步建议
```

## P2 · 网格、摆放与协同（引擎第一部分）

```
任务：实现 packages/engine 的 grid.ts，对应 docs/02 §4 与 §5.5。

必须实现：
1. effectiveSize(size, rot)：本作所有物品都是实心矩形，rot 90/270 等价于宽高互换。
2. itemCells(item)：返回物品占据的所有格子坐标。
3. validateBuild(side, grid)：返回问题列表（越界 / 重叠 / 星级非法 / 未知物品 id）。
   ★ 占用键必须包含**背包页号**：不同页面上坐标相同的两件物品绝不算相邻、绝不算重叠。
4. computeSynergies(side)：返回 Map<itemIndex, {stat: value}>，表示**该物品从邻居获得了什么加成**。
   ★ 语义（docs/02 §5.5，极易写错）：物品 i 的每条 synergy 规则，对它**符合 withTag 的邻居**各提供 add；
     最多影响 maxStacks 个邻居（按数组顺序取前 N 个）。**加成是给邻居的，不是给自己的。**
   ★ 只有正交贴边算相邻，斜角不算；跨背包页不算。

必须写的单元测试（每条一个用例，全部要有明确断言）：
- 旋转后尺寸互换，且 validateBuild 不再报越界
- 两件物品重叠 → 报重叠；三件同格 → 报两处重叠
- 同一坐标但不同背包页 → 合法且**不产生协同**
- 斜角相邻 → 不产生协同
- mana_gem 贴 1 把武器 → 该武器 +5 atkPct；贴 3 把 → 只有前 2 把各 +5（maxStacks=2）
- 协同加成不落在持有规则的那件物品自己身上

DoD：pnpm test 全绿，并贴出「斜角不算相邻」与「加成归属邻居」两个用例的真实输出。
```

## P3 · 战斗结算引擎（**最关键的一轮，必须先于 UI 完成**）

```
任务：实现 packages/engine/battle.ts 的 simulate()，严格按 docs/02 §6 逐条实现。
参考实现是 tools/engine.mjs —— 你可以读它来对照，但**不要直接复制文件**，
要按规格用自己的结构写，否则差分测试就失去意义了。

必须严格实现的要点（每一条都是高频错因）：
1. tick 模型：TICK_MS=100，MAX_TICKS=600。战斗是 tick 循环，不是真实时间。
2. 开局：所有物品 cdRemaining=0（开局即就绪，会形成一波齐射）。
3. 行动顺序：round 为偶数 → A 先 B 后；奇数 → B 先 A 后。
   每方内部按 (背包页, row, col) 升序显式排序。
4. ★ 每方行动结束后**立即**判定死亡并结束本 tick。
   若改成"双方都行动完再判定"，同阵容互殴会 100% 平局（docs/02 §6.3 有实测记录）。
5. 冷却：cdRemaining 递减发生在该方被处理的那一刻；同一 tick 内先手方扣冷却不影响后手方。
   耐力不足时物品**不激活且不重置冷却**，下 tick 再试。
6. 伤害：raw = (value*starMult + buffs.atkFlat) * (1 + min(atkPct+职业动态加成, 300)/100) * atkScale
   → 暴击判定 → **Math.floor(raw)** → 再扣护甲。
   ★ 先取整再扣护甲；护甲不衰减；blocked = min(target.block, raw)。
7. 护甲不衰减；每 tick 末 stamina/hp 回复**只在"本 tick 未分出胜负"时**执行。
8. 属性上限（docs/02 §6.5）超限直接丢弃，不是衰减。
9. 超时（满 600 tick）按 hp/maxHp 比例判胜负，比例相等判平局。
10. 突然死亡：tick ≥ rules.battle.suddenDeath.fromTick 时全体伤害 ×damageMult。
11. 回合生命成长：maxHp *= (1 + rules.battle.hpGrowthPerRound * (round-1))，对双方同时生效。
12. 职业特性：战士狂暴（按已损失生命动态加 atkPct）、游侠先手、法师暴击基线、牧师开场回复。
13. 随机流：mulberry32(deriveSeed(matchSeed, round, buildFingerprint(side)))。
    ★ 种子绑定**阵容指纹**而不是左右位置 —— 保证换边后结果镜像对称。
14. simulate 支持可选参数 firstStrikeSide（默认 null = 按回合奇偶），仅用于 QA 构造对称用例。
15. 输出 BattleLog，字段与 docs/02 §6.7 **完全一致**（多一个字段都算不合格）：
    每 tick 必须有一条 type:'state' 事件，否则无法做差分测试。

另外必须实现 CLI：
  pnpm -F engine sim:dump --seed <n> --round <n> --a <buildA.json> --b <buildB.json> --out <eval.json>
  输出 { seed, round, a, b, log }。可用 tools/sim-dump.mjs 作为样板（用法见其头部注释）。

DoD（必须全部满足，并贴出真实输出）：
1. pnpm test 全绿；上面 15 条每条至少一个单测。
2. 跑通并贴出：
   pnpm -F engine sim:dump --seed 1 --round 7 --a <a.json> --b <b.json> --out out/eval.json
   node tools/diff-test.mjs --evals out
   结果必须是「完全一致 N 个，存在差异 0 个」。
   （a.json / b.json 可用 node tools/sim-dump.mjs --demo --out out 先生成做对照）
3. 若差分测试报出差异，**不要改 tools/ 里的裁判**，改你的引擎直到 0 差异。
   把每一处差异的定位与你的修法写进交付说明。

不要做：不要为了"看起来合理"而偏离 docs/02；不要动 tools/ 与 data/。
```

## P4 · 商店与经济

```
任务：实现 packages/engine 的 shop.ts，对应 docs/02 §7。

必须实现：
1. 商店抽卡：格位数按 rules.shop.slotCountByRound；稀有度按 shop.rarityWeightsByRound 的回合权重抽取；
   物品池 = 玩家职业专属物品 + neutral；**其他职业专属物品不得出现**。
2. 保底：连续 shop.pityRareAfterDryRounds 回合没有出现 rare 及以上时，下一回合强制至少 1 个 rare。
3. 传奇唯一：同一局内已持有的 legendary 不再出现。
4. 经济：收入 = baseIncome + 回合加成 + 利息(每 interestPerGold 金 +1，上限 interestCap)；
   胜利 +winBonus；连胜 ≥winStreakThreshold 额外 +winStreakBonus。
5. 刷新：首次 rerollBaseCost，本回合内每次 +rerollCostStep，回合结束重置。
6. 出售返还 max(sellRefundMin, floor(cost * sellRefundRatio))。
7. 背包扩容（金币出口）：第 unlockRound 回合起解锁，价格 = baseCost + costStep × 已购次数，
   给**当前最高解锁页**增加 rowsPerPurchase 行，每页最多 maxExtraRowsPerPage 行。
   ★ 扩容后该页的有效尺寸变大，必须传进 validateBuild/simulate（这是易错点：
     扩容后物品会落在新增的行上，若校验仍按基础尺寸会误报越界）。
8. 三合一升星：3 件同 defId 同星级 → 1 件 +1 星；**原位保留第一件的位置**，不要挪到列表末尾
   （列表顺序即装箱/结算顺序，挪位会造成不可复现的行为差异）。

DoD：
- 单测覆盖：抽卡不越池、保底触发、传奇唯一、利息上限、扩容后布局合法、三合一原位保留。
- 写一个 1000 次的模拟脚本，统计每回合商店里"至少 1 件买得起"的比例，应 ≥ 95%。
  贴出真实输出。
```

## P8 · Bug 修复循环提示词（第 4 步用）

把 QA 报告直接附在这个提示词后面。

```
任务：修复 QA 报告中的缺陷。报告在 reports/qa-report-*.md 与 reports/diff-*.md。

【工作方式】
1. 先按级别排序：S0 → S1 → S2。S0（结算错误 / 不确定 / 卡死）必须最先修。

4. 严禁为了让测试通过而修改 tools/ 或 data/ 里的期望值。裁判（tools/engine.mjs）是规格的可执行版本，
   改它等于改考试答案。唯一的例外：数据确实违反 docs/02（此时要说明依据，并同步更新 docs/02）。
5. 严禁用 try/catch 吞掉错误、严禁用默认值掩盖非法状态。宁可抛错也不要静默算错。

【每修一条，必须输出】
- 缺陷编号与级别
- 根因（具体到代码行为，不要写"逻辑问题"这种废话）
- 修改的文件与关键 diff
- 复现步骤的**修复后实际输出**（贴命令与输出，不要写"应该已修复"）
- 是否有同类问题（同一个根因在别处是否也存在）→ 若有，一并修

【收尾】
- 跑 node tools/validate-data.mjs 与 node tools/qa-check.mjs，贴出完整输出。
- 若报告里含 tools/diff-test.mjs 的差异项，修完后必须重跑并贴出"存在差异 0 个"。
- 最后给出：已修 N 条 / 未修 M 条（附原因）/ 新引入的问题（如有）。
```

## 附：贴提示词时容易踩的坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 让 GPT-6 同时写引擎和 UI | 在算错的引擎上调动画，双重返工 | 严格按 P3 → P5 顺序 |
| 不给 `tools/engine.mjs` 和 `data/` | 它会自己发明数值，和你的策划书对不上 | P0 里已要求把整个目录作为上下文 |
| 不说"以 docs/02 为准" | 遇到含糊处它自己拍板，事后很难改 | P0 已写明冲突时的优先级 |
| 不让它贴真实输出 | "已完成"但实际没跑，Bug 留到后面 | 每个 P 都有 DoD + 要求贴输出 |
| 允许它改 `tools/` | 差分测试被架空，等于没测 | P3/P8 明确禁止 |
| 一次给全部提示词 | 上下文过载，质量下降 | 一轮一个 P |
