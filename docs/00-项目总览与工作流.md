# 00 · 项目总览与工作流

## 1. 产品定位

| 项 | 内容 |
|---|---|
| 类型 | 单人 PvE 自走棋 / 背包构筑（auto-battler + inventory management） |
| 参照 | Backpack Battles、Backpack Hero、Super Auto Pets（对手曲线与命值） |
| 平台 | Web（桌面浏览器优先，最小宽度 1280；移动端仅做只读观战） |
| 单局时长 | 目标 **8–14 分钟**，约 12–18 回合 |
| 美术风格 | 二选一：①像素风（低成本、AI 友好）②扁平矢量（更耐看、外包更贵）。MVP 用① |
| 技术栈 | 前端 Vite + TypeScript + React（UI/背包）+ Canvas（战斗表现）；后端 Node + Fastify + Socket.IO + SQLite |

### 为什么是"背包"这个题材
背包格子是**稀缺资源**，它把"数值成长"变成了"空间取舍"——玩家每一次买物品都在做真实决策，
天然规避了自走棋最容易死的地方：无脑堆一件最强装备。所以本作的**核心乐趣 = 摆放策略**，
战斗只是摆放结果的结算。这条要贯穿所有设计：**任何削弱摆放决策权重的功能（自动摆放、一键最优）
都不做**，只提供"撤销/回退"。

## 2. 角色分工

| 角色 | 职责 | 不该做的事 |
|---|---|---|
| **你（制作人）** | 定风格、买/找资源、跑验收、拍板砍需求 | 不要自己改数值；改平衡走 `data/rules.json` |
| **GPT-6（开发）** | 按 `docs/02` + `docs/03` 实现前后端、写单测、自检、修 Bug | 不要自行发明规则；规则冲突时以 `docs/02` 为准并在回执里提出 |
| **我（QA / 裁判）** | 维护 `data/rules.json` 与 oracle、跑自动化检测、出可玩性与 Bug 报告 | 不替 GPT-6 改业务代码（避免"既当运动员又当裁判"） |

## 3. 交接物（Handoff）与门禁（Gate）

```
[你] 资源 MVP 清单 ──► Gate 1: 每件物品都有占位图或正式图，manifest.json 合法
        │
        ▼
[GPT-6] P0~P7 提示词 ──► Gate 2: pnpm dev 能跑通完整一回合循环；pnpm test 全绿
        │
        ▼
[我] tools/qa-check.mjs + diff-test.mjs ──► Gate 3: 无 S0/S1；9 项指标达标或给出调参项
        │
        ▼
[GPT-6] P8 修复提示词 ──► Gate 4: 逐条回执 + 回归门禁（qa-check 重跑）不退化
        │
        └──► 循环到 Gate 4 稳定通过，进入内容量扩充（加物品/职业/关卡）
```

**门禁原则**：Gate 不通过不进入下一阶段。宁可 MVP 只有 20 件物品，也不要 40 件物品 + 跑不起来的循环。

## 4. 三条不可协商的工程约束

### 4.1 引擎与表现分离
```
packages/engine/      ← 纯 TS，零 DOM 依赖，可在 Node 里 headless 跑
packages/data/        ← data/*.json + zod schema
apps/web/             ← React + Canvas，只读引擎输出的战斗日志做动画
apps/server/          ← 存档、排行榜、伪 PvP 对手快照
```
战斗表现必须是**回放**：引擎一次性算完得到 `BattleLog`，前端按 tick 播放。
这样才有：可回放、可 skip、可倍速、可断线重连、可 diff 测试。**不允许边渲染边计算。**

### 4.2 确定性（Determinism）
- 随机只用种子化 PRNG（推荐 mulberry32 / xorshift128），种子由 `(matchSeed, round)` 派生。
- 禁止 `Math.random()`、`Date.now()`、`performance.now()` 参与逻辑。
- 遍历顺序必须显式排序（按 `slotIndex`），不得依赖 `Object.keys` 顺序。
- 验收：同种子跑 100 次，日志哈希完全一致（`qa-check` 会自动验证）。

### 4.3 数据驱动
- 所有数值：物品伤害/冷却/价格、经济参数、命值、关卡曲线 → `data/*.json`。
- 代码里出现魔法数字 = 缺陷（`qa-check` 会扫描 `damage: 7` 这类字面量并告警）。
- `data/rules.json` 是唯一平衡入口，改数值必须只改这一个文件族。

## 5. 为什么需要 oracle（数值裁判）

自走棋的 Bug 大多不是崩溃，而是**数值悄悄错了**：冷却多算了一帧、护甲结算顺序反了、
相邻加成在旋转后丢失、升星后乘算变加算。这些靠人眼测不出来，靠"感觉不对"更测不出来。

所以我们在 `tools/engine.mjs` 里维护一份**规则的独立参考实现**，并强制 GPT-6 实现
**规范战斗日志**（见 `docs/02` §6.7）。于是验收变成机械动作：

1. 用同一个 seed / 同一套双方阵容，分别跑游戏引擎和裁判；
2. 逐 tick 对比 HP、护甲、耐力、每个物品的冷却与激活事件；
3. 第一处不一致即定位到**具体 tick + 具体物品**，直接进 Bug 报告。

这就是第 3 步"检测可玩性、生成错误代码报告"能真正落地而不用我逐帧玩的原因。

### 5.1 工具链分工

| 工具 | 作用 | 什么时候跑 |
|---|---|---|
| `tools/validate-data.mjs` | 数据体检（字段/引用/区间/布局/描述一致性） | 每次改 `data/` 之后 |
| `tools/run-balance.mjs` | 贪心 AI 跑整局 → 九项指标 + 难度曲线 + 物品分布 | 每次改数值之后 |
| `tools/calibrate.mjs` | 依据实测胜率自动标定关卡难度旋钮 | 平衡指标不达标时，迭代 3–6 轮 |
| `tools/gen-enemies.mjs` | 生成 18 关阵容（多背包页装箱、确定性） | 要改关卡阵容时 |
| `tools/sim-dump.mjs` | "游戏引擎必须提供的 sim:dump CLI" 的参考样板 | 给 GPT-6 做对照 |
| `tools/diff-test.mjs` | 差分测试，逐 tick 定位数值差异 | GPT-6 每次改引擎之后 |
| `tools/qa-check.mjs` | 一键全检 → QA 报告 + Bug 列表（退出码即门禁） | 每个阶段收尾 |

### 5.2 已被工具链抓到的真实缺陷（证明这套流程有效）

| # | 缺陷 | 后果 | 抓它的工具 |
|---|---|---|---|
| 1 | 开局所有物品冷却为 0 → 第一 tick 全体齐射 | 一回合爆发 ≈ 整条血条，战斗 1 tick 就结束 | 平衡模拟（平均战斗时长 0.1–2 秒） |
| 2 | 金币没有出口（背包买满后无事可做） | 终局囤积 70 金，玩家"有钱没事干" | 平衡模拟（指标 4） |
| 3 | 协同加成加给了持有规则的那件物品自己，而不是邻居 | 全部协同的实际效果与策划书不符 | 写裁判时对照规格发现 |
| 4 | 18 关对手只用第 1 页背包（30 格），而玩家后期有 78 格 | 后期难度曲线整体塌陷 | 平衡模拟（难度曲线 90–100% 胜率） |
| 5 | 合并升星把物品挪到列表末尾，破坏了贪心装箱顺序 | 出现"上回合装得下、这回合装不下"的**卡死**状态 | 平衡模拟（抛错定位到具体回合与物品清单） |
| 6 | 随机流按左右位置派生 | 换边后结果不镜像 → 位置优势 | 公平性测试（换边违规 70%） |

> 这 6 条没有一条能靠"玩一下"发现。这就是 L2 逻辑层检测的价值。

## 6. 时间盒建议（单人 + AI 协作）

| 阶段 | 产出 | 建议时长 |
|---|---|---|
| 资源 MVP（占位图 + 音效） | `assets/manifest.json` | 0.5–1 天 |
| GPT-6 实现引擎 + 单测 | `packages/engine` 通过裁判差分测试 | 1–2 天 |
| GPT-6 实现前端循环 | 可玩一局（无美术） | 2–3 天 |
| QA 第一轮 | `reports/qa-report-*.md` | 0.5 天 |
| Bug 修复循环 | ≥ 3 轮收敛 | 1–2 天 |
| 内容扩充（40→80 物品、8 职业） | 数据文件 | 2–3 天 |

**MVP 的"完成"定义**：一局能玩完、能看到胜负、能重开、9 项指标达标。
不包含：联机、排行榜、成就、剧情、多语言。
