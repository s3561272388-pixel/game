## 1. 一句话与核心循环

**一句话**：把买来的物品塞进有限背包，摆完自动开打，靠摆放、协同与升星赢下 18 个回合。

**核心循环（每回合 4 个阶段）**

```
① 商店 (SHOP)      刷新/购买/出售/冻结   ── 花金币做构筑决策
② 摆放 (PREPARE)   拖拽/旋转/合并升星     ── 核心乐趣所在（空间取舍）
③ 战斗 (BATTLE)    自动结算，逐 tick 播放 ── 验证摆放结果
④ 结算 (RESULT)    收入/掉血/连胜统计     ── 反馈与压力
        └──────────────── 进入下一回合（更难）────────────────┘
```

**设计红线（不要违反）**
1. 不提供"自动最优摆放"。只提供撤销（Ctrl+Z，最近 20 步）与按类型排序。
2. 战斗中玩家不影响结果，但**必须可跳过/4 倍速**（否则重复对局会烦）。
3. 每回合都必须让玩家做一次**有代价的取舍**（金币不够 / 格子不够 / 协同冲突，至少一个成立）。

## 4. 背包与摆放规则

### 4.1 网格
- 尺寸：**6 列 × 5 行 = 30 格**。坐标 `col ∈ [0,5]`，`row ∈ [0,4]`，原点左上。
- 每个玩家可以拥有**多个背包页**：MVP 只有第 1 页；第 5 回合解锁第 2 页（6×4=24 格），
  第 11 回合解锁第 3 页。购买时可指定放入哪一页。**页与页之间不产生相邻协同。**

### 4.2 物品尺寸
允许尺寸（宽×高，旋转后互换）：`1×1, 1×2, 1×3, 1×4, 2×2, 2×3, 3×3`。
- 武器偏长条（1×2 ~ 1×3），防具偏方正（2×2 ~ 2×3），饰品偏小（1×1）。
- **尺寸即强度**：3×3 的传家宝占据 9 格，数值必须配得上机会成本（见 §16 平衡旋钮）。

### 4.3 合法摆放
1. 物品所有格子必须在背包边界内；
2. 不与任何已有物品的格子重叠；
3. 允许背包内存在空洞（不要求完全填满，但空洞会带来机会成本）；
4. 允许旋转 0 / 90 / 180 / 270 度；
5. 战斗中物品**不可移动**（除非该物品效果明确写"移动"）。

### 4.4 交互清单（对应可玩性指标 #8，缺一即 Bug）
- 拖拽放置：吸附到最近合法格；非法位置**红色高亮 + 抖动反馈 + 禁止落地**；
- 悬停预览：把手中物品悬停在背包上时，实时显示"若放这里，将获得哪些协同加成"（+N 数值飘字）；
- 旋转：右键点击 / `R` 键（在手里时）；
- 出售：拖到商店区域，或右键菜单"出售（返还 60% 金币）"；
- 撤销：`Ctrl+Z` 回退最近 20 步摆放/买卖操作；
- 提示缺失：任何操作被拒绝时必须有可见原因（金币不足 / 没有空间 / 已达上限）。

## 5. 物品系统

### 5.1 字段定义

```ts
type Rarity = 'common' | 'uncommon' | 'rare' | 'epic' | 'legendary';
type ClassId = 'warrior' | 'ranger' | 'mage' | 'cleric' | 'neutral';
type StatKey = 'damage' | 'heal' | 'block' | 'staminaGain' | 'atkPct' | 'atkFlat' | 'speedPct'
             | 'critChance' | 'critMult' | 'lifesteal' | 'thorns' | 'regenPerTick' | 'healPct'
             | 'maxHp' | 'maxStamina' | 'staminaRegen';
type Trigger = 'on_battle_start' | 'on_activate' | 'on_hit_taken' | 'on_kill' | 'on_low_hp';

interface ItemEffect {
  trigger: Trigger;
  op: 'damage' | 'heal' | 'block' | 'buff' | 'stamina' | 'drain';
  stat?: StatKey;     // op='buff' 时必填
  value: number;      // 基础值，受星级乘区影响
  durTicks?: number;  // 临时效果（MVP 不做，留位）
}

interface ItemDef {
  id: string;                 // 蛇形：wpn_rusty_sword
  name: string;               // 中文名
  cls: ClassId;               // 职业归属，neutral 为通用
  rarity: Rarity;
  size: [number, number];     // [w, h]
  cost: number;
  tags: string[];             // ['weapon','melee','sword'] 等，协同判定用
  cooldown: number;           // 秒；被动/持续类填 0
  staminaCost: number;        // 每次激活消耗耐力
  melee?: boolean;            // 是否近战（受反伤 thorns 影响）
  effects: ItemEffect[];
  synergy?: { withTag: string; stat: StatKey; add: number; maxStacks: number }[];
  desc?: string;              // 面向玩家的说明（必须与实际效果一致，QA 会抽查）
}
```

### 5.2 稀有度与价格

| 稀有度 | 价格 | 主要获取回合 | 强度定位 |
|---|---|---|---|
| common | 2 | 1+ | 填充物，靠协同与升星变强 |
| uncommon | 4 | 2+ | 构筑骨架 |
| rare | 7 | 4+ | 流派核心 |
| epic | 11 | 7+ | 单件质变 |
| legendary | 16 | 10+ | 定义流派的胜负手，全局唯一（同一局只能持有 1 件同名 legendary） |

### 5.3 升星（合并）
- 规则：**同 `defId` 且同星级** 的 3 件 → 自动合成 1 件星级 +1（保留 `slotIndex` 最小者的位置与旋转，其余消失）。
- 星级乘区（作用于所有 `effect.value`）：`1星 ×1.0`，`2星 ×1.8`，`3星 ×3.2`。上限 3 星。
- 合并必须播放明显反馈（金光 + 音效 + 数值变化对比），且**不可撤销**（因此合并前需二次确认，或提供"锁定自动合并"开关）。

### 5.4 冻结
商店中可冻结单个格子，使其保留到下一回合（不消耗，不刷新）。冻结上限 3 个格子。

### 5.5 协同（Adjacency Synergy）
- 判定：两物品存在**正交贴边**即为相邻；斜角不算。
- 生效：某个物品的每条 `synergy` 规则，对**每一个符合条件的邻居各叠加一次**，但**最多 `maxStacks` 次**（规则里硬性要求 ≤ 3）。
- 方向无关：旋转、谁左谁右都算。
- 跨背包页无效（不同页面坐标相同也**不算相邻**，实现时占用键必须带页号）。
- UI 必须可视化：相邻时连接线发光 + tooltip 里显示当前实际加成来源列表。
- **结算时机**：全部协同在战斗开始时**一次性**算完，折算成战前 buff（与 `on_battle_start` 效果同等处理），
  战斗中不再重新计算；因此协同提供的 `maxHp` 会正确影响开局生命上限。超限部分按 §6.5 截断。

**示例**：`法力宝石` 的 `synergy: {withTag:'weapon', stat:'atkPct', add:5, maxStacks:2}`
→ 它旁边贴着 1 把武器时，那把武器 `atkPct +5`；贴着 3 把时仍然只 +10（封顶 2 层）。

### 5.6 物品池与解锁
- 商店按回合权重抽取，权重表见 `data/rules.json → shop.rarityWeightsByRound`。
- 已解锁职业的物品 + `neutral` 物品进入池子；**其他职业的专属物品不出现**（避免污染）。
- 保底：连续 2 回合没有出现任何 `rare` 及以上的物品时，第 3 回合强制至少 1 个 `rare`。

## 6. 战斗结算规则（**权威章节 / 验收依据**）

> 这一节必须逐条实现。任何偏离都会被 `tools/diff-test.mjs` 精确抓出来。

### 6.1 时间模型
- `TICK_MS = 100`；`MAX_TICKS = 600`（60 秒）。
- 战斗是**回合制 tick 循环**，不是真实时间。前端按 tick 播放日志，允许 1×/2×/4× 与直接跳过。

### 6.2 初始状态
| 字段 | 来源 |
|---|---|
| `maxHp` | 职业基线 + 所有物品 `on_battle_start` 的 `maxHp` 加成 + 相邻协同 |
| `hp` | 开局 = `maxHp`，再叠加职业特性（如牧师开场回复） |
| `maxStamina` / `staminaRegen` | 职业基线 + 物品加成 |
| `stamina` | 开局 = `maxStamina` |
| `block` | 0（除物品开场给护甲） |
| `buffs` | 职业特性 + 物品 `on_battle_start` 的 `buff` + 协同加成（见 §5.5） |
| 每个物品 `cdRemaining` | 0（开场即就绪，除非 `on_battle_start` 写明延迟） |
| **回合生命成长** | `maxHp *= (1 + rules.battle.hpGrowthPerRound × (round-1))`，**对双方同时生效** |
| 敌方缩放 | 再乘 `side.hpScale`（伤害则乘 `side.atkScale`），仅用于关卡难度标定 |

> **为什么需要"回合生命成长"**：玩家阵容的输出会随物品数量、星级、协同成长约 6–10 倍，
> 而基础生命只涨 1.3 倍左右。若不加这个刻度，后期战斗会在 **1 个 tick 内结束**
> （本项目已实测复现：平均战斗时长 0.1–2 秒）。它同时作用于双方，因此不改变阵营强弱，
> 只把"打到第几回合"换算成血量刻度，让战斗时长在整局中保持稳定（目标 6–45 秒）。

### 6.3 每 tick 的执行顺序（严格）
```
for tick in 0 .. MAX_TICKS-1:
    1. 决定本 tick 的行动顺序：round 为偶数 → A 先 B 后；round 为奇数 → B 先 A 后
       （保证先手权在整局中交替，消除位置优势）
    2. for side in [先手方, 后手方]:
         for item in side.items 按 (背包页, row, col) 升序:      # slotIndex 显式排序
             if item.cdRemaining > 0: item.cdRemaining -= 1; continue
             if item.staminaCost > side.stamina: continue        # 耐力不足则原地等待
             activate(item)                                       # 见 6.4
         # ★ 每方行动结束后立即判定死亡，命中即结束本 tick
         if 任一方 hp <= 0: break 出本 tick
    3. 若本 tick 未分出胜负：双方 tick 末处理
         stamina = min(maxStamina, stamina + staminaRegen)
         hp      = min(maxHp, hp + regenPerTick)
         block   不衰减
    4. 记录本 tick 的 state 事件；判定结束：任一方 hp<=0 → 结束；tick == MAX_TICKS → 按 hp 比例判定
```
**注意**
- `cdRemaining` 递减发生在该方被处理的那一刻，同一 tick 内先手方扣冷却不会影响后手方。
- **「每方行动后立即判定」不是可选优化，是必需规则。** 若改为「双方都行动完再判定」，
  同阵容互殴会因双方在同一 tick 内等量掉血而 **100% 平局**（本项目的平衡模拟已实测复现，
  见 `reports/balance-*.md`）。这条规则让先手权变得有意义，而先手权由回合奇偶交替来平衡。

### 6.3.1 突然死亡（sudden death，防僵局）
当 `tick ≥ rules.battle.suddenDeath.fromTick`（默认 400，即第 40 秒）时，
**双方造成的伤害统一乘以 `suddenDeath.damageMult`**（默认 2.0）。

> **为什么必须有这条**：没有它时，双方都堆护甲/回复的阵容会互相打不死，
> 约 3.5% 的战斗会打满 600 tick，然后按血量比例判定平局——而平局双方都掉命，
> 玩家体验极差且无法通过操作改善。加了这条之后超时率降到 0.43%。
> 玩家可见的表现：第 40 秒起背包整体泛红 + 屏幕边缘脉冲 + 提示"决死时刻"。

### 6.3.2 QA 专用参数 `firstStrikeSide`
`simulate(opts)` 支持可选参数 `firstStrikeSide`（默认 `null` = 按回合奇偶交替）。
它**只用于 QA 构造对称用例**：固定先手方后交换左右阵容，验证"引擎不存在任何位置相关逻辑"。
游戏实现不需要在 UI 层暴露它，但引擎函数需要接受它，否则差分测试无法构造镜像用例。

> 常见错误构造（本项目踩过）：交换左右阵容时如果不一起翻转先手方，实际是把先手权也换了人，
> 那是两个不同的对局，不是镜像。正确的对称性判据是：
> **跑 A：X 在左槽且左槽先手；跑 B：X 在右槽且右槽先手** → 两次结果必须完全镜像。

### 6.4 activate(item) 结算
```
for effect in item.effects where trigger == 'on_activate'（按数组顺序）:
    v = effect.value * STAR_MULT[item.stars]

    op = 'damage':
        raw = (v + buffs.atkFlat) * (1 + min(buffs.atkPct + 职业动态加成, 300)/100)
        if rand() < min(buffs.critChance,100)/100: raw *= buffs.critMult      # 默认 critMult=1.5
        raw     = floor(raw)
        blocked = min(target.block, raw); target.block -= blocked
        dealt   = raw - blocked; target.hp -= dealt
        if item.melee and target.buffs.thorns > 0:
            tb = min(attacker.block, min(target.buffs.thorns,30)); attacker.block -= tb
            attacker.hp -= (min(target.buffs.thorns,30) - tb)
        if buffs.lifesteal > 0: attacker.hp = min(maxHp, attacker.hp + floor(dealt * min(lifesteal,50)/100))

    op = 'heal':    hp = min(maxHp, hp + v * (1 + buffs.healPct/100))
    op = 'block':   block += v
    op = 'buff':    buffs[stat] = min(CAP[stat], buffs[stat] + v)     # CAP 见 6.5
    op = 'stamina': stamina = min(maxStamina, stamina + v)
    op = 'drain':   target.stamina = max(0, target.stamina - v)

激活后：
    item.cdRemaining = max(1, round( item.cooldown / (1 + min(buffs.speedPct,200)/100) / 0.1 ))
    side.stamina    -= item.staminaCost
```
- 取整规则：所有最终伤害/治疗数值 **向下取整**（`Math.floor`）后再作用于 HP；`block` 允许小数，仅显示时取整。**取整时机必须与裁判一致**，这是最常见的 diff 来源。
- 随机数：只有暴击用到 PRNG。PRNG 每个玩家独立一条流，种子 `= hash(matchSeed, sideIndex)`，保证一方是否暴击不影响另一方抽到的随机序列。

### 6.5 属性上限（防指数爆炸，硬性）
| 属性 | 上限 | 属性 | 上限 |
|---|---|---|---|
| `atkPct` | 300 | `thorns` | 30 |
| `speedPct` | 200 | `regenPerTick` | 5 |
| `lifesteal` | 50 | `critChance` | 100 |
| `critMult` | 3.0 | `maxStamina` | 40 |

超限部分**直接丢弃**（不是衰减）。

### 6.6 胜负判定
| 情况 | 结果 |
|---|---|
| 一方 `hp ≤ 0`，另一方 `> 0` | 另一方胜 |
| 同一 tick 双方都 `≤ 0` | 平局（双方各 -1 命） |
| 到 `MAX_TICKS` | `hp/maxHp` 高者胜；相等 → 平局 |
| 胜 | 玩家不掉命，+1 金币（+连胜奖励） |

### 6.7 战斗日志（规范格式，前端与裁判共用）
```ts
interface SideSpec {
  cls: ClassId;
  items: { defId: string; stars: 1|2|3; page?: number; col: number; row: number; rot: 0|90|180|270 }[];
  name?: string;
  hpScale?: number;    // 关卡难度旋钮，默认 1
  atkScale?: number;   // 关卡难度旋钮，默认 1
  pages?: [number, number][]; // 该方**实际生效**的背包页尺寸（含扩容加的行）；缺省用 rules.unlock.pageSizes
}
interface BattleLog {
  version: '1.0';
  seed: number; round: number;
  sides: [SideSnapshot, SideSnapshot];      // 战前快照：职业、maxHp、pages、物品列表（含 page/col/row/rot/stars）
  events: BattleEvent[];                     // 按 tick 升序
  ticks: number;                             // 实际进行到第几 tick
  winner: 'A' | 'B' | 'draw';
  finalHp: [number, number];
}
```
> `pages` 必须出现在 SideSpec 里：背包扩容后物品会落在**新增的行**上，
> 若校验仍按基础 6×5 网格，会误报越界（本项目踩过这个坑）。
type BattleEvent =
  | { t: number; type: 'activate'; side: 0|1; slot: number; itemId: string }
  | { t: number; type: 'damage';   side: 0|1; target: 0|1; amount: number; blocked: number; crit: boolean }
  | { t: number; type: 'heal';     side: 0|1; amount: number }
  | { t: number; type: 'block';    side: 0|1; amount: number }
  | { t: number; type: 'buff';     side: 0|1; stat: StatKey; value: number; total: number }
  | { t: number; type: 'stamina';  side: 0|1; value: number; total: number }
  | { t: number; type: 'state';    t: number; hp: [number,number]; block: [number,number]; stamina: [number,number] }  // 每 tick 末一条
  | { t: number; type: 'end'; winner: 'A'|'B'|'draw' };
```
**日志必须逐 tick 完整**（含每 tick 末的 `state`），否则无法做差分测试。

## 7. 商店与经济

| 参数 | 值 |
|---|---|
| 商店格位 | 6 个（第 1–3 回合），第 4 回合起 7 个 |
| 每回合基础收入 | `10 + floor((round-1)/4)` 金 |
| 利息 | 回合结束时，每存 5 金 +1（上限 +3） |
| 胜利奖励 | +1 金；连胜 ≥3 时额外 +2 |
| 刷新商店 | 首次 1 金，本回合内每次 +1，回合结束重置为 1 |
| 出售返还 | `max(1, floor(cost * 0.6))` |
| 冻结 | 最多 3 格，免费 |
| 初始金币 | 10 |
| **背包扩容** | 第 3 回合解锁。花费 `8 + 4×已购次数` 金，给当前背包页**增加 1 行**（每页最多 +3 行） |

> **为什么必须有扩容这个出口**：背包只有 30 格。物品买满后金币无处可花，玩家会在终局
> 囤积 60+ 金币，出现"钱很多但无事可做"的体验缺陷。平衡模拟已实测复现该问题
> （见 `reports/balance-*.md` 指标 4）。扩容同时把"空间"这一核心稀缺资源变成了可投资项，
> 强化了本作的核心乐趣。

**经济健康的目标**
- 终局未花费金币 ≤ 累计总收入的 **25%**（说明钱基本能花出去）；
- 任意连续 2 个回合内，至少存在 1 件买得起且装得下的物品。

## 9. 关卡与对手（PvE 伪 PvP）

- 共 **18 回合**。第 18 回合后仍存活 → 通关胜利。
- 对手数据来自 `data/enemies.json`，每关：`{round, name, cls, hpScale, atkScale, items:[{defId, stars, page, col, row, rot}]}`。
- **该文件由 `tools/gen-enemies.mjs` 生成，不要手改布局。** 生成规则：按「目标阵容价值曲线」
  （`6 + 5.4×(round-1)`，上限 104）挑选物品，稀有度按回合权重抽取，逐件装箱到已解锁的背包页；
  每关强制至少 2 件输出装；第 12 回合起部分物品升为 2 星。结果完全确定性。
  - 改阵容 → 改生成器的价值曲线与物品池规则，重新生成；
  - 改难度 → 用 `tools/calibrate.mjs` 调 `hpScale`/`atkScale`（依据实测胜率自动标定）。
- 难度目标：全 18 关的**实测胜率**必须落在 `rules.enemyCurve.winRateBandsByRound` 的区间内
  （送分局 70–98%，决胜期 30–65%）。这是**实测值**，不是设计者的主观判断。
- **前 3 关为送分局**，预期玩家胜率 > 70%。
- 对手随机浮动：`hpScale` 与 `atkScale` 各乘 `1 ± 0.08`，用 `(matchSeed, round)` 派生，保证同种子可复现。
- 设计意图：让玩家在第 4–8 关第一次感受到"必须开始做协同，而不是堆单件"。

## 10. 命值与失败

- 初始 **5 命**。输 -1，平局双方各 -1。
- 任意时刻命 ≤ 0 → 本局结束（游戏失败结算页）。
- 不掉命的情况：胜利。
- 结算页必须展示：存活回合数、最高单次伤害、最终流派标签（按物品 tag 统计占比最高的两个）、金币总收入、物品图鉴收集数。

## 15. 数值基线

- **40 件初始物品**的完整数值见 `data/items.json`（common 14 / uncommon 10 / rare 8 / epic 5 / legendary 3）。
- **4 个职业**见 `data/classes.json`；**18 关对手**见 `data/enemies.json`。
- **全部可调旋钮**见 `data/rules.json`（战斗常量、经济、掉落权重、属性上限、星级乘区）。

### 15.1 数值设计公式（新增物品时按此推导，保证同稀有度强度一致）
```
期望 DPS      ≈ damage / cooldown_effective
耐力约束      DPS_eff = DPS * min(1, staminaRegen / (staminaCost / cooldown))
每金 DPS      ≈ 0.8（common）→ 1.4（legendary）递增
防御物品      block/cooldown ≈ 该稀有度攻击物品 DPS × 0.8
治疗物品      heal/cooldown  ≈ 该稀有度攻击物品 DPS × 0.6
```
**尺寸惩罚**：占据格数 `A` 的物品，其"每金强度"应与 `A` 成**反比但不低于 0.7 倍**
（大件更亏格子，所以要稍微超模一点点才有人用）。

## 19. 可玩性验收指标（详见 `docs/04`）

| # | 指标 | 阈值 | 判定方式 |
|---|---|---|---|
| 1 | 开局可操作性 | 每回合 ≥1 件可负担物品的概率 ≥95% | 模拟 2000 局 |
| 2 | 单局时长 | 平均 12–18 回合（8–14 分钟） | 模拟 + 前端埋点 |
| 3 | 公平性 | 镜像对局 A 方胜率 ∈ [45%, 55%]，平局率 ≤10% | 模拟 2000 场 |
| 4 | 经济健康 | 终局未花费 ≤ 累计收入 25%；连续买不起 ≤ 2 回合 | 模拟 |
| 5 | 无秒杀 / 无爆炸 | **单次最高伤害 < 对方 maxHp**（不可满血秒杀）；单件物品伤害占比 ≤70%；打满 600 tick 的超时率 ≤1% | 模拟 |
| 6 | 构筑多样性 | 每个物品在**其所属职业**的终局阵容中出现率 ≥5%；前 10 物品占终局槽位 ≤45% | 模拟统计 |
| 7 | 确定性 | 同种子 100 次结果哈希一致 | `qa-check` |
| 8 | 交互完整性 | 5 类操作 0 异常（见 §4.4） | 自动化 + 人工 |
| 9 | 性能 | 600 tick 结算 ≤16 ms；UI 稳定 60fps | benchmark |

> **指标 5 的口径说明**：早期版本用的是"单次伤害 ≤ maxHp 的 55%"这一拍脑袋阈值，
> 模拟实测最坏值 62%（2 星传奇打到 85 血的法师）。该阈值既无设计依据、又会逼着砍废传奇武器。
> 真正要守住的不变量是**「不可满血秒杀」**（单次伤害 < 对方 maxHp）与**「不可一件定胜负」**
> （单件伤害占比 ≤70%），因此指标 5 改用这两个口径。
