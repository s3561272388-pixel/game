# 04 · 可玩性验收与测试方案

> 本文回答一个问题：**凭什么说这个游戏"能玩"？**
> 答案是九项可量化指标 + 一套可执行的检测工具链，而不是"我玩了一下感觉还行"。

---

## 1. 三层检测体系

| 层 | 检测对象 | 工具 | 能抓到什么 | 抓不到什么 |
|---|---|---|---|---|
| **L1 数据层** | `data/*.json` | `tools/validate-data.mjs` | 字段缺失、引用错误、数值越界、布局重叠/越界、价格与稀有度不符、DPS 超模、描述与数值不符、tag 拼错导致协同永不生效 | 逻辑错误 |
| **L2 逻辑层** | 战斗/商店引擎 | `tools/diff-test.mjs`（差分）<br>`tools/qa-check.mjs`（确定性/性能） | 逐 tick 数值偏差、事件顺序错误、非确定性、随机流失效、性能退化 | UI 手感 |
| **L3 体验层** | 完整对局 | `tools/run-balance.mjs`（贪心 AI 模拟）<br>人工清单（见 §5） | 难度曲线、经济健康、公平性、时长、构筑多样性、僵局 | 真正的"好玩" |

**关键点**：L2 的差分测试是整套体系的地基。它把"我觉得数值不对"变成
「第 137 tick，第 1 方第 3 号物品伤害 7 ≠ 8」这种可以立刻修的东西。

---

## 2. 九项可玩性指标（与 `data/rules.json → qaThresholds` 一一对应）

| # | 指标 | 阈值 | 判定工具 | 为什么是它 |
|---|---|---|---|---|
| 1 | 开局可操作性 | 存在可负担物品的回合 ≥ 95% | run-balance | 防止"开局就没得选"的挫败 |
| 2 | 单局时长 | 平均 12–18 回合；贪心 AI 通关率 35–65% | run-balance | 太短没有构筑感，太长会疲劳；通关率给出难度区间 |
| 3 | 左右对称性 | 换边违规 = 0；先手优势 ≤ 75%；僵局率 ≤ 10% | run-balance | 换边违规 = 引擎存在位置相关逻辑（严重缺陷）；先手优势过大 = 硬币游戏 |
| 4 | 经济健康 | 未花费 ≤ 总收入 25%；连续买不起 ≤ 2 回合 | run-balance | 金币必须有出口，否则玩家"有钱没事干" |
| 5 | 无秒杀 / 无爆炸 | 单次伤害 < 对方 maxHp；单件伤害占比 p95 ≤ 80% 且最坏 ≤ 95%；超时率 ≤ 1% | run-balance | 不可满血秒杀；不可一件物品决定胜负 |
| 6 | 构筑多样性 | 死件率 ≤ 20%（其余参考） | run-balance | 有物品没人用 = 内容浪费或数值失衡 |
| 7 | 确定性 | 100 次同种子结果完全一致；随机流按 (seed, round, 阵容指纹) 派生 | qa-check | 回放、断线重连、申诉核查的前提 |
| 8 | 交互完整性 | 9 项交互清单全部通过（见 §5） | 人工 | 拖拽手感无法自动判定 |
| 9 | 性能 | 单场结算 ≤ 16 ms；UI 稳定 60 fps | qa-check + 人工 | 4 倍速播放不能掉帧 |

### 2.1 关于阈值修订（诚实记录）

本项目的阈值经历过一次真实修订，过程记录如下，供后续维护参考：

| 指标 | 初版阈值 | 实测 | 修订为 | 修订理由 |
|---|---|---|---|---|
| 5 单次伤害上限 | ≤ maxHp 的 **55%** | 最坏 62% | 改为「单次伤害 < maxHp」+「单件占比 p95 ≤80%、最坏 ≤95%」 | 55% 无设计依据，会逼着砍废 2 星传奇武器。真正要守的是"不可满血秒杀"与"不可一件定胜负" |
| 5 单件伤害占比 | ≤ **70%**（max） | p95 55%、最坏 69%（修好敌人阵容构成后） | p95 ≤80%，并新增最坏 ≤95% 的硬不变量 | 用极值当闸门会被个别畸形对局主导；p95 更稳健 |
| 2 贪心 AI 通关率 | 10–40% | 45–53% | 35–65% | 贪心 AI 是**接近最优**的玩家代理（永不失误、永远按性价比买），它的通关率是真人通关率的**上界**，不是下界。真人通关率必须在实机测试中单独测量 |
| 6 出现率上限 | 所有物品 ≤95% | 起始物品恒为 100% | 起始物品排除出判定；出现率改为告警 | 起始物品每个职业开局就有，天然 100%，不是"必买物品"问题 |

> **纪律**：修订阈值必须留痕（原因 + 实测数据），且**必须先确认不是实现 bug**。
> 本项目在修订指标 5 之前，先修掉了两个真实实现缺陷（开局全体齐射、敌人阵容缺输出装），
> 修订后的数据是修复后的数据，不是"把及格线降低到当前水平"。

## 3. 自动化检测流程（每次改动后都跑）

```powershell
cd G:\dsh\backpack-brawl

# ① 数据体检（秒级）
node tools/validate-data.mjs

# ② 全量回归：平衡 + 确定性 + 性能 → 生成 QA 报告
node tools/run-balance.mjs --runs 500
node tools/qa-check.mjs

# ③ 若游戏仓库已存在，加做源码静态扫描（引擎纯净性）
node tools/qa-check.mjs --src ..\backpack-brawl-src

# ④ 差分测试（GPT-6 每完成一次引擎改动都要跑）
node tools/diff-test.mjs --self-test                     # 先确认评测器本身可用
node tools/diff-test.mjs --evals <游戏 sim:dump 输出目录>
```

**门禁（Gate）**：`qa-check` 的退出码即门禁。要求 **无 S0、无 S1、无 FAIL 检查项**。
`qa-check` 会同时输出 Markdown 与 JSON 两份报告：Markdown 给人看，JSON 给 GPT-6 读。

### 3.1 调难度曲线的标准动作

```powershell
node tools/run-balance.mjs --runs 300     # 测
node tools/calibrate.mjs                  # 依据实测胜率写回 enemies.json 的 hpScale/atkScale
# 重复上述两步 3–6 轮直到难度曲线全部落进设计区间
node tools/run-balance.mjs --runs 800     # 用更大样本复核
```

`calibrate.mjs` 的调节逻辑：**两个旋钮各管一个目标**——
`atkScale` 管胜率（实测偏高 → 提高敌人攻击），`hpScale` 管战斗时长（打得太快 → 加敌人血）。
两个目标分开控制，避免互相打架。单轮调整幅度限幅 ±35%，防止过冲。

### 3.2 关卡阵容是生成出来的，不要手改

`data/enemies.json` 由 `tools/gen-enemies.mjs` 生成。原因：
1. 后期关卡必须占用第 2/3 页背包（玩家在 R5/R11 解锁新页），手写多页布局极易重叠/越界；
2. 关卡强度要跟经济曲线挂钩，手写无法保证单调。

改阵容 → 改生成器里的目标价值曲线与物品池规则 → 重新生成 → 跑 validate + balance。
改难度 → 用 `calibrate.mjs` 调 `hpScale`/`atkScale`。

## 4. 差分测试：怎么用、怎么看结果

### 4.1 契约

游戏引擎必须提供：

```
pnpm -F engine sim:dump --seed <n> --round <n> --a <a.json> --b <b.json> --out <eval.json>
```

输出：

```json
{ "seed": 1, "round": 7, "a": { "cls": "...", "items": [...] }, "b": { ... }, "log": { BattleLog } }
```

`BattleLog` 的字段定义见 `docs/02 §6.7`。`tools/sim-dump.mjs` 是这份契约的参考样板。

### 4.2 结果解读

| 报告里的类型 | 级别 | 最可能的根因 |
|---|---|---|
| 伤害数值不符 | S1 | 取整时机（应先乘加成再 floor 再扣甲）、护甲扣减顺序、暴击倍率上限 |
| 每 tick 血量不符 | S1 | 耐力不足时的等待规则、每 tick 末回复顺序、死亡判定时机 |
| 事件顺序/类型分歧 | S1 | 同 tick 内的行动顺序、排序键（必须按 页,row,col） |
| 战斗时长不符 | S1 | 冷却换算（cd / (1+speedPct/100) / 0.1，最小 1 tick）、初始 cd |
| 胜负判定不符 | S0 | 超时判定的 hp 比例、平局条件 |
| 开局属性不符 | S1 | on_battle_start 与协同的叠加顺序、回合生命成长、敌方缩放 |
| 耐力不符 | S2 | 耐力消耗与回复的取整（耐力允许小数，只在显示时取整） |

> 评测器自身也要被验证：`node tools/diff-test.mjs --self-test` 用裁判对比裁判，必须 0 差异。
> 本项目已验证它会抓到注入的 bug：人为把伤害 +1、把某 tick 血量 -3，报告会精确指出
> 「tick 0：裁判 hp=[235,166]，游戏 hp=[235,163]」。

## 5. 人工验收清单（不可自动判定，必须实机做）

每项都必须在 **1280×720 与 1600×900 两种分辨率**下各做一遍。

### 5.1 交互手感（对应指标 8）

| # | 项目 | 通过标准 |
|---|---|---|
| 1 | 拖拽放置 | 跟手无延迟无偏移；物品在鼠标中心偏上；合法位置有吸附预览 |
| 2 | 非法放置 | 红色高亮 + 抖动 + 禁止落地；回弹动画 ≤200 ms；不允许瞬间闪现到别处 |
| 3 | 悬停协同预览 | 手持物品悬停时实时显示"放这里会得到哪些加成"，数值与放置后一致 |
| 4 | 旋转 | R 键与右键都能旋转；旋转后占位预览同步变化；不出现越界/重叠 |
| 5 | 合并升星 | 3 件同名同星自动合成；**原位保留**不跳格；有金光与音效；数值按 ×1.8/×3.2 生效 |
| 6 | 出售 | 拖到商店区或右键菜单；返还金额出售前可见；返还 = max(1, floor(cost×0.6)) |
| 7 | 撤销 | Ctrl+Z 连续回退最近 20 步；不可撤销时按钮置灰；撤销买卖时金币同步回滚 |
| 8 | 背包已满购买 | 必须禁止并给出可见原因；**绝不允许**出现买下后放不下的死状态 |
| 9 | 战斗跳过与倍速 | 空格进入战斗；1/2/4 倍速与跳过均可用；跳过直接出结果、不卡死、结算不丢 |

### 5.2 数值与文案一致性

| # | 项目 | 通过标准 |
|---|---|---|
| 10 | Tooltip 数值 | 随机抽 10 件物品，浮窗显示数值 = 实战生效值（含星级与协同） |
| 11 | 金币收支 | 回合结算页的四项数字（收入/利息/连胜/卖出）与 `data/rules.json → economy` 逐项对得上 |
| 12 | 职业特性 | 4 个职业的特性描述与实际表现一致（战士残血变强、游侠先手、法师暴击、牧师治疗加成） |
| 13 | 协同可视化 | 相邻生效时连接线发光，tooltip 里列得出加成来源 |

### 5.3 健壮性

| # | 场景 | 期望 |
|---|---|---|
| 14 | 商店全买不起 | 不卡死，能进入战斗 |
| 15 | 背包全满且无线可扩容 | 能进入战斗，不报错 |
| 16 | 战斗打满 600 tick | 有明确结果（突然死亡规则应已避免僵局） |
| 17 | 刷新页面 | localStorage 恢复当前局（金币/命值/背包/商店/回合） |
| 18 | 连续玩 3 局 | 无内存增长导致的卡顿；无跨局状态泄漏 |
| 19 | 窗口缩放到 1280×720 | 布局不重叠、不遮挡、可操作 |

### 5.4 主观体验必答题（3 个真人各玩 1 局后回答）

1. 你第一次意识到"摆放位置会影响强弱"是在第几回合？（期望 ≤ 5）
2. 你在哪一回合第一次感到"钱不够用/格子不够用"？（期望 6–12；若从未出现说明没压力）
3. 你输掉那局时，能说出自己哪里做错了吗？（期望能；若"莫名其妙就输了"说明信息反馈不足）
4. 你愿意再开一局吗？（期望 ≥ 2/3 的人愿意）

> 第 3 题是本作最重要的体验问题：背包构筑游戏的核心快感来自"我的摆放决策带来了胜负"，
> 如果玩家说不清自己为什么输，说明战斗表现的信息量不够（飘字太少、协同反馈太弱）。

## 6. 验收流程与门禁

```
改动 → ① validate-data  → ② run-balance → ③ qa-check → ④ diff-test → ⑤ 人工清单
         ↓失败              ↓指标不达标      ↓有 FAIL      ↓有差异        ↓有不过
      改 data/            calibrate       看报告修      改引擎         改 UI
```

**Gate 3（进入第 4 步修 Bug 阶段）的准入条件**：
- `validate-data`：0 错误
- `qa-check`：无 S0 / S1，无 FAIL 检查项
- `diff-test`：存在差异 = 0
- 人工清单 §5.1 的 9 项全通过

**Gate 4（可发布 MVP）的准入条件**：
- Gate 3 全部满足
- 人工清单 §5.2 / §5.3 全通过
- §5.4 主观体验题 4 题中至少 3 题达标

## 7. 已知未达标项（截至本项目首次 QA）

诚实记录当前数据的遗留问题，不要假装全绿：

| 项 | 现状 | 影响 | 建议 |
|---|---|---|---|
| 难度曲线 | 18 关中 5 关（R12/R14/R16/R17/R18）胜率高于设计区间 | 后期偏易，决胜期张力不足 | 已由 `calibrate.mjs` 迭代过 15+ 轮仍收敛不动，说明这几关的**阵容构成**而非数值是瓶颈：跑 `gen-enemies.mjs` 调高这几关的输出装下限，或提高 `targetValue` 曲线尾部 |
| 近乎必买物品 | 钉头锤在牧师局出现率 99.5%、双刃在游侠局 99.3% | 削弱构筑选择的意义 | 提升同职业其他 uncommon 的相对性价比（改 `items.json`），而不是砍这两件 |
| 真人通关率 | **未测量** | 无法确认难度是否适合真人 | 必须做 3 人 × 1 局的可玩性测试，用 §5.4 的问卷 |
| 联机 / 排行榜 | 未实现 | 不在 MVP 范围 | 见 `docs/02 §17` |
